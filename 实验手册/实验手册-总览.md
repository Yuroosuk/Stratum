# Stratum 计算机系统实验手册
> 用 C++ 从零构建 RISC-V 32 位计算机系统全栈：模拟器 → 硬件抽象层 → 操作系统


---

## 一、项目简介

**Stratum**（地层）是一套自制的计算机系统软件栈，名字源于"层层叠叠的地层结构"——正如本项目从最底层的硬件模拟一层层向上堆叠，最终支撑起一个能运行用户程序的操作系统。

项目包含四个子系统：

| 子系统 | 简称 | 职责 |
|--------|------|------|
| **Stratum-Core** | SCore | RISC-V 32 位 CPU 模拟器（硬件层） |
| **Stratum-HAL** | SHAL | 硬件抽象层，屏蔽平台差异（系统软件层） |
| **Stratum-OS** | SOS | 简化版操作系统（OS 层） |
| **Stratum-DB** | SDB | 交互式调试器（工具层） |

最终目标：在自己写的模拟器（SCore）上，运行自己写的操作系统（SOS），OS 能加载并运行简单的 C 用户程序（如打印 Hello World、运行简单游戏）。

## 二、实验阶段总览

| 阶段 | 名称 | 核心产出 |
|------|------|----------|
| **PA0** | 环境搭建 | 开发环境 + 项目框架 + 协作流程 |
| **PA1** | 简单调试器 | SDB：表达式求值、watchpoint、寄存器查看 |
| **PA2** | 冯诺依曼计算机 | SCore：RV32I 指令执行，能跑简单 C 程序 |
| **PA3** | 外设与运行时 | SHAL：串口/定时器/键盘/显示器，能跑小游戏 |
| **PA4** | 操作系统 | SOS：系统调用、文件系统、进程管理 |

**总计：约 4～6 周**

## 三、各阶段目标详述

### PA0 — 环境搭建

**目标：** 让两个人能在同一套代码库上协同开发，确保环境一致。

**完成标志：**
- 项目能用 `make` 编译通过（空框架）
- 两人都能正常 push/pull，CI 不报错
- 能看到 `./score` 程序启动并打印 Stratum 欢迎信息

**主要内容：**
- 安装工具链：`g++`、`make`、`riscv32-unknown-elf-gcc`、`gdb`
- 搭建目录结构（见第五节）
- 配置 Git 仓库与分支策略
- 配置 Makefile 构建系统

---

### PA1 — 简单调试器（SDB）

**目标：** 在 SCore 中实现一个交互式调试器，方便后续调试 CPU 执行过程。

**完成标志：**
- `si [N]`：单步执行 N 条指令
- `info r`：打印所有寄存器当前值
- `x N ADDR`：以十六进制打印从 ADDR 起的 N 个字节
- `p EXPR`：对表达式 EXPR 求值并打印（支持四则运算、括号、十六进制数、寄存器引用）
- `w EXPR`：设置 watchpoint，当表达式值变化时暂停
- `d N`：删除编号为 N 的 watchpoint

**验证方式：**
- 手写测试样例，对表达式求值结果与 `bc` 命令对比
- 对寄存器初始值进行断言检查

---

### PA2 — 冯诺依曼计算机（SCore 核心）

**目标：** 实现 RISC-V 32 位 CPU 的取指-译码-执行循环，能够运行编译好的 RISC-V 二进制程序。

**完成标志：**
- 实现 RV32I 全部 47 条基础整数指令
- 能加载并执行一个简单的 `hello.c` 编译出的 ELF 文件
- 自带的测试用例（`cpu-tests`）全部通过
- 可选：实现 RV32M 乘除法扩展

**验证方式：**
- 运行 `cpu-tests` 下所有测试程序，对比 difftest 参考输出
- 使用 SDB 单步跟踪，验证 PC 跳转与寄存器变化符合预期

---

### PA3 — 外设与硬件抽象层（SHAL）

**目标：** 实现 SHAL 硬件抽象层接口，让上层程序能使用 I/O 设备，最终能在 SCore 上运行简单游戏。

**完成标志：**
- 串口输出（UART）：`putch()` 能在终端打印字符
- 定时器：`io_read(AM_TIMER_UPTIME)` 返回正确的毫秒数
- 键盘输入：能读取按键事件
- 帧缓冲（VGA）：能绘制像素到窗口（使用 SDL2 模拟显示器）
- 运行 `hal-tests` 全部通过
- 运行经典 Demo：`打字游戏` 或 `Bad Apple`

**验证方式：**
- `hal-tests` 测试套件逐项通过
- 肉眼确认 SDL2 窗口能正常显示画面

---

### PA4 — 操作系统（SOS）

**目标：** 实现一个能加载和调度用户进程的简化操作系统。

**完成标志：**
- 系统调用框架：`ecall` 陷入内核，分发到对应处理函数
- 基础系统调用：`SYS_write`、`SYS_exit`、`SYS_read`、`SYS_brk`
- 文件系统：支持 ramdisk，能用 `open/read/write/close` 操作文件
- 进程加载：能从文件系统加载 ELF 用户程序并执行
- 分时多任务：实现基于时钟中断的简单轮转调度
- 最终 Demo：SOS 加载并运行 `hello`、`slider` 等用户程序

**验证方式：**
- `stratum-apps` 中的用户程序能正常启动并交互
- 多进程切换下无明显卡顿或崩溃

## 四、双人协作方案

### 分工原则

> 以「层」为单位划分责任，避免频繁在同一文件上冲突。

| 成员 | 主要负责 | 辅助支持 |
|------|----------|----------|
| **成员 A（硬件侧）** | SCore 核心（PA2：指令实现、内存、外设寄存器） | PA1 调试器、PA3 设备模拟 |
| **成员 B（软件侧）** | SHAL + SOS（PA3 HAL接口、PA4 OS） | PA1 表达式解析、PA4 文件系统 |

### Git 协作规范

```
main          ← 稳定版本，只接受 PR 合入，不直接 push
dev           ← 日常集成分支
feature/a(b)/pan  ← PA1 调试器特性分支
bugfix/pan/xxxx(具体bug)
```

**规则：**
1. dev 是合入分支，来自main
2. feature来自dev，结构如上，每个人只能在这个分支开发，且只能开发该pa的功能。
3. bugfix来自dev，是针对已经合入的前置pa某个bug进行修复。

**禁止在某个feature对前面已经合入的pa进行修改，有bug要对接。**


### 接口约定

两人之间的"接口"是最重要的协作边界：

| 接口层 | 定义方 | 实现方 |
|--------|--------|--------|
| `paddr_read/paddr_write`（物理内存读写）| 成员 A | 成员 A |
| `SHAL_IOE` 接口（IO设备抽象）| 成员 B | 成员 B |
| CPU 状态结构体 `CPU_state` | 成员 A 定义 | 双方共用 |
| 系统调用编号表 `syscall.h` | 成员 B 定义 | 双方共用 |

### 独立开发与分层联调

> **核心原则：不需要等对方完成才能联调。** 每一层都有独立的运行和测试手段，双方可以并行推进，分层渐进地对接。

#### 成员 A（SCore 硬件层）的独立调试方式

SCore 是一个完全独立的可执行程序，不依赖 SHAL 或 SOS 的任何代码。

| 调试手段 | 说明 |
|----------|------|
| 直接加载 `.bin` 文件 | 用 `riscv32-unknown-elf-gcc` 编译一个最简单的汇编/C程序为裸机二进制，直接喂给 SCore 执行 |
| `cpu-tests` 测试套件 | 项目自带一批独立的小型 RISC-V 测试程序，覆盖各类指令，A 可以单独跑，无需 B 参与 |
| SDB 单步跟踪 | 用自己写的调试器，逐条指令检查 PC 和寄存器变化是否符合 RISC-V 规范 |
| difftest（可选）| 与 Spike（官方 RISC-V 模拟器）逐指令对比输出，精确定位指令实现错误 |

#### 成员 B（SHAL/SOS 软件层）的独立调试方式

SHAL 设计了 `native` 平台——直接编译运行在开发者的 Linux/macOS 上，**完全绕过 SCore**，B 可以在 A 的模拟器尚未完工时就全速推进。

| 调试手段 | 说明 |
|----------|------|
| `ARCH=native` 编译 | SHAL 的所有接口在 native 上有对应实现（用 Linux 系统调用），B 可以直接在本机运行和调试 |
| `hal-tests` on native | HAL 的键盘/定时器/显示接口测试套件，先在 native 跑通，再切到 SCore 平台 |
| SOS on native | OS 代码同样可以先在 native 平台运行，文件系统、ELF 加载器都可以独立测试 |
| 单元测试 | klib（轻量 C 库）、文件系统等模块可以写独立的 main() 驱动测试，不依赖任何模拟器 |

#### 分层渐进联调时机

两人不是"都做完再联调"，而是按以下节点**分批对接**：

```
[PA2 中期] A 完成 SCore 基础执行循环（能跑 cpu-tests）
               ↓
           第一次联调：B 把 klib/hal-tests 编译为 riscv32 二进制，
                       在 A 的 SCore 上跑，验证内存和基础指令正确
               ↓
[PA3 初期] B 完成 SHAL 的 UART/定时器（native 已验证）
               ↓
           第二次联调：在 SCore 上打通 putch()，确认串口输出正常
               ↓
[PA3 末期] A 完成 VGA/键盘外设寄存器，B 完成 SHAL 的 IOE 接口
               ↓
           第三次联调：在 SCore 上跑 SDL2 显示，能看到画面
               ↓
[PA4 中期] B 完成 SOS 系统调用框架（native 已验证）
               ↓
           第四次联调：在 SCore 上运行 SOS，加载第一个用户程序
```

## 五、项目目录结构（规划）

```
stratum/
├── score/                 # SCore：CPU 模拟器（PA1、PA2）
│   ├── src/
│   │   ├── cpu/           # 指令执行核心
│   │   ├── memory/        # 内存系统
│   │   ├── device/        # 外设模拟（UART、VGA、键盘）
│   │   ├── monitor/       # SDB 调试器
│   │   └── utils/         # 工具函数
│   ├── include/
│   └── Makefile
├── shal/                  # SHAL：硬件抽象层（PA3）
│   ├── include/
│   └── src/
│       ├── riscv/         # RISC-V 平台相关实现
│       ├── native/        # 本机测试平台实现
│       └── klib/          # 轻量级 C 标准库
├── sos/                   # SOS：操作系统（PA4）
│   ├── src/
│   │   ├── fs.cpp         # 文件系统
│   │   ├── proc.cpp       # 进程管理
│   │   ├── syscall.cpp    # 系统调用
│   │   └── loader.cpp     # ELF 加载器
│   └── include/
├── stratum-apps/          # 用户程序（PA4 验证）
│   ├── apps/
│   │   ├── hello/
│   │   └── slider/
│   └── libs/
└── Makefile               # 顶层构建入口
```
